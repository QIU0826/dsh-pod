# 技术调研：Token 开销 / 上下文控制 / harness 间传输协议

> 调研日期：2026-08-29 ｜ 目的：为 dsh-pod 的三个关键技术难点找可借鉴的学术工作与开源实现
> 证据分级沿用方案书惯例：**A 级**＝本次联网检索到原文/官方文档；**B 级**＝检索到二手转述或训练知识，细节需复核

---

## 0. 一句话结论

三个难点里，**token 开销与上下文控制有成熟且可直接落地的方案（成本归因 + 引用传递 + 懒加载工具定义）**；
**传输协议方面最有价值的一条信息是：ACP 已于 2025-08 并入 A2A**——本项目 `docs/adapters.md`
里「ACP 预留」的措辞已经过时，应改为 A2A。此外项目的自研 satellite 协议与 A2A 的 Agent Card
模型高度相似，值得考虑兼容而非另立。

## 1. Token 开销

### 1.1 可借鉴的工作

| 工作 | 级别 | 要点 | 对 Pod 的用处 |
|---|---|---|---|
| **Token Economics for LLM Agents**（浙大 + 阿里云，arXiv 2605.09104，46 页综述） | A | 双视角框架（计算机科学 × 经济学）：token 是生产要素 / 交换媒介 / 记账单位。四维分类：单 Agent（微观）→ 多 Agent（中观）→ 生态（宏观）→ 安全 | **现成的成本归因语言**。把账本从「记总数」升级为「按 token 类别分桶」的理论依据 |
| **Token Efficiency in AI Agent Systems**（openstandardagents.org） | A | 给出 MCP 工具定义开销的实测数字与协议级优化策略表 | 直接对应本项目的 MCP 暴露面 |
| **AgentTaxo / Tokenomics**（arXiv 2601.14470，转述） | B | 用 ChatDev + GPT-5 跑 30 个软件开发任务，实证 token 分布与「通信税」概念 | 与本项目的 bake-off 方法论同构，可作为扩样参照 |
| **GLM（Huan et al. 2025-11）** | B | 把整块 Graph-CoT 提示拆成专门 agent + 选择性上下文共享：**token −95.7% 且准确率 +38%** | 「架构分解 + 上下文投影」是高杠杆优化的实证 |
| **SupervisorAgent** | B | Smolagent/GAIA 上 token −29.7%；OAgents 上 −39.4%（L1 最高 −50.2%），精度不降 | 监督者剪枝思路，可启发看板/DAG 的派发策略 |
| **AgentPrune / AgentDropout / SafeSieve / S²-MAD** | B | 通信链路剪枝与辩论稀疏化，剪掉冗余消息/低贡献 agent | 对应本项目的「独立 review 质量门」成本优化 |

### 1.2 值得记住的硬数字

- OpenRouter 周 token 处理量：2024-12 的 **0.4 万亿** → 2026-03 的 **27.0 万亿**（15 个月 ×68）。
- **ChatDev 场景中，迭代式代码 review 消耗了 59.4% 的 token**（转述自 Tokenomics）。
  → 对照本项目：独立 review 是不可关的质量门，但它的成本占比从未被单独度量过。
- agentic coding 的 token 消耗可达单轮推理的 **1000 倍**，**输入 token 主导（>150:1）**。
  → 优化输出长度是低效的，真正的大头在输入上下文、历史回放、失败重试。
- **MCP 工具定义开销**：单个工具 130–270 tokens（工具名+描述 30–80、input schema 80–150、
  JSON 语法 20–40）。接 100 个工具 = **13,000–27,000 tokens**，占 200K 窗口的 **6.5–13.5%**——
  在一次工具调用发生之前就已消耗掉。
- 同一任务的 token 用量存在高达 **30 倍方差**（调度与失败路径差异）。

### 1.3 对 Pod 的具体建议（按性价比排序）

1. **账本增加「阶段归因」维度**（高价值，改动小）
   现有 `Ledger.summary()` 已有 `bySlot` / `byModel` / `byTask`，但缺**按阶段（plan / implement /
   review / replan / 失败重试）**的分类。ChatDev 的 59.4% 说明 review 极可能是最大单项成本——
   没有归因就只能靠感觉优化。建议：`Task.type` 已知，按 type 聚合即可落地。
2. **MCP 工具定义懒加载**（中价值）
   项目暴露 9 个 `pod_*` 工具（开销约 1.2k–2.4k tokens，尚不致命），但若未来接入外部 MCP server
   （即今日落地的 `mcp-gateway.ts`），工具数会膨胀。建议 gateway 的 `listTools` 支持按需返回，
   并在 prompt 里只注入当前任务相关的工具 schema。
3. **失败路径单独计数**（中价值）
   重试、回滚、blocked→重派 的 token 目前混在总账里。建议落 `attempts` 维度的聚合，
   与「30 倍方差」的来源直接对应。
4. **早期止损（early exit）**（中价值，需谨慎）
   连续 N 轮无新证据 / 同一测试重复失败 / 工具返回同类错误 → 切换策略或转人工。
   项目已有 watchdog（空闲/墙钟）与 stall guard，但** watchdog 按时间触发，不按「信息增量」触发**——
   这是可以补的一层。

## 2. 上下文控制

### 2.1 项目现状（已是同类里做得扎实的）

- `session-tiers.ts`：三档会话生命周期 + 70% 阈值重置摘要（方案书 3.2 / CR-01-6）
- `memory.ts`：2.8.1 长期记忆（类型化图谱 + reflection + `pod_mem_*` 三件套）
- `handoff.ts`：交接四件套 + 2×3 投递矩阵——本质是**结构化交付而非自然语言转述**
- `verifier.ts`：产物校验（commit/parent/白名单/叙事一致性）
- 审查者只收 diff 区间与产物摘要（`agent_relay` 事件实测可见）

### 2.2 可借鉴的工作

| 工作 | 级别 | 要点 | 对 Pod 的用处 |
|---|---|---|---|
| **NOOA（NVIDIA，arXiv 2607.20709）** | A（方案书已收录） | harness 六大能力；**引用传递实测 216,806 → 700 tokens（−99.68%）**；记忆 vs 文件笔记 +11.8 RHAE | 已在 2.8.1 与 3.6-S7 落地，是本项目最有说服力的既有优势 |
| **Anthropic 多 agent 研究系统实践** | B（方案书已收录） | reviewer 只收 diff 防锚定、并行 subagent、明确记录协调开销 | 已支撑 2.5 节审查者最小上下文设计 |
| **Optima / CodeAgents** | B | 用 YAML 角色说明 + Python 风格伪代码替代长篇自然语言系统提示；agent 间通信可压缩 | 与 handoff 四件套同向，可进一步压缩交接 payload |
| **跨 agent KV cache 复用**（KVComm / TokenDance / DroidSpeak） | B | 多 agent 重复 prefill 相似上下文 → 共享 KV cache | **本项目不适用**：员工是独立 CLI 进程、跨 vendor 异构，拿不到 KV 层 |
| **Letta / MemGPT 式分层记忆** | B | 显式主存/外存换页 | 项目已有 memory + session-tiers 的等价物，边际收益有限 |

### 2.3 判断

上下文控制这块**不建议大改**。项目的 handoff（结构化交付）+ session-tiers（阈值摘要）+
memory（主动策展）已经是论文里推荐的组合。真正值得补的只有两点：

1. **信息增量式止损**（见 1.3 第 4 条）——当前只有时间维度，没有"是否还在产生新信息"的维度。
2. **交接 payload 的进一步结构化**：handoff 目前是四件套文本，可考虑对大字段（diff、报告全文）
   走**文件指针 + 引用**而非内联（NOOA 的引用传递思路在交接环节的延伸）。项目其实已经有
   「大对象不落事件，走文件指针」的纪律，但 handoff 四件套是否严格遵循需核实。

## 3. harness 间传输协议

### 3.1 协议格局（A 级，本次检索）

| 协议 | 发起方 / 时间 | 定位 | 传输 | 治理 |
|---|---|---|---|---|
| **MCP** | Anthropic，2024-11 | 垂直：agent ↔ 工具 | stdio、HTTP/SSE；JSON-RPC 2.0 | Linux Foundation |
| **A2A** | Google，2025-04；2025-06 捐给 Linux Foundation | 水平：agent ↔ agent 任务委派 | HTTP、SSE、gRPC；JSON-RPC 2.0 | Linux Foundation |
| **ACP** | IBM/BeeAI，2025-03 | 多 agent 协作 + 状态管理 | REST | **2025-08 已并入 A2A** |
| **AG-UI** | CopilotKit，2025 | agent → 前端事件流 | HTTP/SSE、WebSocket | 社区 |
| **ANP** | ANP Working Group，2025 | 去中心化 agent 网络（DID + JSON-LD） | HTTP、P2P | 社区 |

**关键结论：这些协议是互补而非竞争关系**，工业界普遍按层叠加使用：
MCP 管工具、A2A 管 agent 间委派、AG-UI 管前端事件流、ANP 管开放网络身份。

2025-11 的 MCP 规范修订新增：无状态 HTTP 核心、**Tasks 扩展（长时任务）**、OAuth 风格授权、
服务端渲染 UI（MCP Apps）。

### 3.2 对 Pod 的三条具体建议

1. **修正 `docs/adapters.md` 的 ACP 表述**（必做，成本极低）
   ACP 已于 2025-08 并入 A2A，新项目应使用 A2A。文档里「ACP 接入预留」应改为
   「A2A 接入预留」，并说明 ACP 概念（Agent Manifest / Run / Await / Session）如何映射到 A2A。
2. **satellite 协议考虑对齐 A2A Agent Card**（中价值，需权衡）
   项目的 `satellite-server.ts` 提供 `/detect /start /events /kill /health`，语义上非常接近
   A2A 的「能力发现 + 任务委派 + 流式更新」。对齐 Agent Card 的好处是能与
   Salesforce Agentforce、ServiceNow Now Assist、Azure AI Foundry、Amazon Bedrock AgentCore
   等已支持 A2A 的平台互通；代价是要接受外部 schema。**建议先记录为 v0.4 方向，不急改**。
3. **前端事件流可参考 AG-UI 的事件分类**（低价值，可选）
   项目的 SSE 帧（kind + payload）与 AG-UI 的「文本 / 工具调用 / 状态更新 / 生命周期事件」
   模型几乎同构。若未来要支持第三方前端，对齐 AG-UI 能省一层适配。

### 3.3 协议安全（必须在实现时守住）

- **MCP**：工具描述被视为可信内容是主要风险面——存在 tool poisoning（工具元数据藏恶意指令）
  与 **Rug Pull**（工具静默改写定义以窃取凭据）。第三方 MCP server 必须做描述静态审查 +
  运行时监控 + 最小权限。
  → 对应：本次落地的 `mcp-gateway.ts` 已强制「gated 工具过审批门 + 输出截断 + 调用审计」，
  但**尚未对下游工具描述做静态审查**，这是值得补的一点。
- **A2A**：无签名 Agent Card / 无注册中心 / 无 scope 受限 token 时，存在冒充、上下文投毒、重放；
  描述字段注入可劫持任务路由。缓解：Agent Card 内容视为不可信输入，不直接喂给规划模型。
  → 对应：若未来接 A2A，绝不能把远端 Agent Card 的文本直接进 planner 上下文。

## 4. 尚未解决 / 需进一步验证

1. 上述多数论文为**转述**（B 级），GLM 的 −95.7%、ChatDev 的 59.4% 等数字建议按标题检索原文复核后
   再写进方案书或对外材料。
2. MCP 工具定义开销的 130–270 tokens/工具 是基于 cl100k_base 的估算，实际值随 schema 复杂度浮动。
3. 跨 agent KV cache 复用类工作（KVComm 等）对本项目**不适用**，因为员工是跨 vendor 的独立
   CLI 进程，无法共享 KV 层——这条应在方案书中明确排除，避免误投入。
4. A2A 的 2026 1.0.1 版本新增签名 Agent Card 与 Agent Payments Protocol，若真要对接，
   应以该版本为基准重新评估。
