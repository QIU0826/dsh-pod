## 0. 摘要：最值得做的 7 件事

一个总体判断：本项目「编排器居中、原始事件不进 commander、指令进/摘要出、预算双闸」的架构
方向与 Anthropic 多 agent 工程文（orchestrator-worker、子 agent 只回蒸馏结果）一致，
**主要浪费不在架构而在三处微观层**：每轮重复全量工具定义、重试/重派不复用前缀、重置摘要的
整份重写。下面逐项展开。

行业背景锚点：Anthropic 自测数据，单 agent 约为普通聊天 4× token、多 agent 系统约 15×；
多 agent 框架的上下文重复率有实测高达 MetaGPT 72% / CAMEL 86% / AgentVerse 53%（Galileo
汇总，二手口径）——本项目中心化设计已规避其中大部分，剩余优化重点是上面 7 项。

## 1. Token 开销优化

### 1.1 工具定义分层加载（P0，直接收口审计 P0-3）

**现状**：commander 每轮 LLM 调用固定带 3–5K tokens 工具定义，且「阶段大半工具用不上」。
这是行业通病：Atlassian 工程实践披露单个大型 MCP server 每请求仅工具描述就消耗 10K–30K+
tokens；单个工具的 JSON Schema 描述约 200–500 tokens，工具数线性膨胀（Augment Code / agen.co
汇总，二手口径）。

**论文/规范依据**：
- **RAG-MCP**（arXiv:2505.03275）：调用前先用语义检索从外部索引选出相关 MCP/工具，只把选中
  的工具描述给模型，prompt token 削减 50%+，MCP 压力测试中工具选择准确率从 13.x% 升到
  43.13%（3 倍以上）——工具越多，「少给」反而「选得更准」，与 Context Rot（§2.2）互相印证。
- **ToolRAG**：~50% prompt token 下降、工具选择准确率约 3×。
- **Anthropic 社区 DTL（Dynamic Tool Loading）架构提案**：压缩索引（name + category +
  一句话）+ 按需展开完整 schema，声称消息前上下文可降 85–95%；Anthropic 官方已上线
  Tool Search / deferLoading 类能力（服务端 BM25 检索后以 tool_reference 展开）。
- **IETF ADOL 草案**的 tag-based retrieval（按标签过滤，无需向量库，见 §3.1）。

**落地建议（精确到本项目）**：
1. commander 的 pod_* 工具按 mission stage 分组：`plan / dispatch / verify / approve /
   memory / cron / ...`（与 `by_stage` 归因口径共用一套枚举）。
2. 每轮调用只注入：① 当前 stage 工具的**完整 schema**；② 其余工具的**一行索引**
   （`pod_xxx — 一句话用途 — stage 标签`）；③ 一个固定的 `pod_expand_tool(name)` 元工具，
   模型判断需要跨 stage 工具时先展开、下一轮再调用。
3. 起步不需要 embedding：stage 状态在编排器里是确定的，用确定性 tag 过滤即可（ADOL 的
   Approach 2）；工具数继续增长后再上 BM25/语义检索。
4. MCP 对外暴露面（`mcp-server.ts`）同步实现 `tools/list --short` 协商（§3.1）。

**验证**：复用 bakeoff 基建做 A/B：old=全量工具，new=分层；主指标 `by_stage` 的
plan/approve 阶段 input tokens/轮；护栏指标=工具选择错误率（调用不存在/错 stage 工具的
比例）、任务成功率不回归。预期每轮省 2–4K tokens × commander 轮数。

### 1.2 静态前缀工程与 prompt cache 对齐（P0，治「重试付 3 倍」）

**现状**：档位 B 靠 `--session-id/resume`，档位 C 达阈值销毁重建；重试、review 重派、replan
都会重新走一遍完整 prompt。`buildTaskPrompt` 每轮动态拼装，字段顺序/时间戳/动态措辞任何
字节级变动都会使 provider 侧 KV cache 前缀失效。

**依据**：
- **Prompt caching 机制**（Anthropic / OpenAI 官方文档）：缓存命中的输入 token 按约 10%
  计费（Anthropic）；OpenAI 对 ≥1024 token 的前缀自动缓存、命中约 5 折；缓存是**前缀匹配**，
  动态变量必须放在静态块之后，否则命中率归零。Anthropic 允许最多 4 个显式断点，断点打在
  「后续请求共享的最后一个块」（通常是 system / 工具定义），不能打在占位 user 消息上。
- 厂商/工程博客口径：100K 长 prompt 首 token 延迟可从 ~11.5s 降到 ~2.4s（Zylos 汇总，二手）。

**落地建议**：
1. 固定 worker/commander prompt 的**段落顺序与静态文本**，形成分层前缀：
   `[charter+纪律(静态)] → [工具完整 schema(按 stage 半静态)] → [tenets(mission 级静态)]
   → [重置摘要/记忆(delta 可变)] → [本次 task spec/steer(动态)]`。越稳定越靠前。
2. 动态内容（时间戳、事件 seq、随机措辞）全部移到最后一段；同 mission 重试时前 3 段必须
   字节一致——加一个快照测试：同一任务两次 build 的前缀块 hash 相等。
3. CLI 是黑盒：确认 claude/codex 各 adapter 是否透传/默认开启 provider cache（Claude Code
   会话内默认利用），在 `ledger.ts` 增加 cache_read/cache_creation token 列（CLI verbose
   usage 若提供），把**缓存命中率变成可观测指标**，否则此项无法闭环。
4. 重试场景：结构类失败的直接重试（现状 P1 feedback 环里结构类分支）天然应全前缀命中；
   语义类失败写回 spec 时，只让最后一段变化，保证前面全部命中。

**验证**：账本新增 cached_input_tokens 占比；对比重试任务的二次 input 计费 token。

### 1.3 review 上下文：hunk 级两级加载替代定长截断（P1）

**现状**：review 注入 diff ≤40K 字符 + spec ≤2K + summary ≤1.5K，超长截断或 need_clarify。
问题：截断按长度不按相关性，关键 hunk 可能被切；审查者拿到的仍是「一大段 diff」。

**依据**：
- **Agentless**（arXiv:2407.01489）：分层定位（文件 → 类/函数 → 编辑点），不养长上下文
  agent，单任务成本约 $0.34，而 SWE-agent 约 $4.19（约 12× 差，论文/复述口径），修复率
  反而更高——「少而准」胜「多而杂」。
- **SWE-Edit（viewer–editor 分解）**：浏览子 agent 负责找上下文、编辑主 agent 只收窄上下文，
  整体成本 −17.9%、解决率 +2.1%。
- **SWE-Pruner**（2026）：任务感知的自适应剪枝，0.6B 小 skimmer 按当前任务目标筛上下文。
- 多支团队独立量化：coding agent 67–76% token 花在读文件/搜索/终端输出上，有用证据埋在
  噪声里（Codex KB 汇总四篇论文，二手口径）。

**落地建议**：
1. 宿主在生成 review spec 时，先产出**变更地图**：文件清单 + 每个 hunk 的标题级摘要
   （函数名/变更类型/行数），这是第一级，永远全量、很小。
2. 第二级才是 hunk 正文：按与任务 spec 的相关度排序（确定性关键词/路径匹配起步，无需
   模型），在字符预算内从高到低装；预算外的 hunk 保留在地图里，审查者可通过既有
   fs-browse 端点按索引**主动拉取**（它本就无仓库写权限，符合三道防线）。
3. 截断事件要带「被切掉的是哪些 hunk」元数据落盘（现在只有截断事实），供 verifier 判断
   审查覆盖度，也供事后 bakeoff。

**验证**：A/B 对比「40K 定长截断」vs「两级加载」的 review 发现缺陷数、review input tokens、
误报率；预期 review 派发 token 再降 30–50%（参照 SWE-Edit/Agentless 量级，需自测确认）。

### 1.4 自然语言侧的 token 级压缩（P2，限定场景）

**依据**：LLMLingua（EMNLP 2023，小模型按困惑度删 token，宣称最高 20×）；LLMLingua-2
（ACL 2024 Findings，token 级二分类，2–5× 压缩、LongBench 上性能损失 <5%，355M 模型约
0.3s）。**Acon**（arXiv:2510.00615，微软，长程 agent 专项）：同时压缩环境观测与交互历史，
峰值 token −26–54% 且成功率不降反升；消融显示 history 4096 / observation 1024 token 的
中等压缩阈值最优，过小会因频繁压缩掉点；压缩指南可用失败轨迹对比自动优化，单 benchmark
优化成本 <$2，压缩器可蒸馏到小模型（保留教师 95% 表现）。

**本项目判断（克制使用）**：
- 代码/diff/MISSION_REPORT 是高密度文本，token 级删改风险高，**不压缩**。
- 可压缩对象仅限自然语言：IM 出站摘要、产物叙事摘要、reflection 输入、长期记忆蒸馏输入。
- 若做，优先 Acon 路线而非 LLMLingua：用「全量成功/压缩后失败」的对比轨迹反演压缩指南，
  且压缩器用小模型/便宜模型，贵模型只留给执行——与项目「措辞 bakeoff 无收益就不投」的
  实证文化一致，先小样本 A/B，无显著收益即停。

### 1.5 多 agent 通信稀疏化（P2，架构已规避大半）

**依据**：AgentPrune《Cut the CRAP》（arXiv:2410.02506）对通信做稀疏化；Agent Dropout
（arXiv:2503.18891）动态淘汰冗余 agent 与通信链路。本项目刻意不做 P2P、由编排器居中，
已经避开这类方法要解决的主要问题。剩余可做的是**差量注入**：replan/重派/换人时，spec
基线不变的部分用引用（指向已落盘 task_context 版本 hash），只把变化的 delta 写成文本，
避免整份 spec 重发；这与 §1.2 前缀缓存同源。另外可在 dispatcher 增加「是否值得派审查
员工」的任务风险分级（低风险机械任务跳过 review 链），属于 Agent Dropout 的弱化确定性版。

## 2. 上下文管理优化

### 2.1 档位 C 重置摘要：从整份重写改为 ACE 式增量 delta 账本（P1）

**现状**：占用 ≥70% 销毁重建，注入「只含已完成任务事实（标题/commit/测试结果）」的结构化
摘要。多次重置意味着摘要被反复重新生成——这正是文献点名的两种失败模式：
**brevity bias**（越压越短、领域细节流失）与 **context collapse**（迭代改写侵蚀细节）。

**依据 — ACE（Agentic Context Engineering，arXiv:2510.04618，Stanford/SambaNova/UC
Berkeley，2025-10，已投 ICLR 2026）**：把上下文当作持续演进的 playbook，Generator/
Reflector/Curator 三角色，**只做局部增量编辑（delta update）而非整份重写**，AppWorld
+10.6%、金融推理 +8.6%、相对强上下文适应基线平均延迟 −86.9%。其前身 Dynamic Cheatsheet。

**落地建议**：
1. 重置摘要持久化为**条目集合**（每条：id / 类型[事实|决策|坑] / 内容 / 来源 commit&event
   seq / 状态[active|superseded]），落盘到 `~/.dsh/pod`，与账本同源管理。
2. 重置时不重新总结全部历史，而是 Curator 式操作：新增本次增量、把被推翻的条目标
   superseded（保留不删，可审计）、合并重复——全部是确定性骨架 + 一次小模型调用。
3. 这与现有 `memory.ts` 的 typed relation（supports/contradicts/derived-from）和 reflection
   合并/剪枝是同一套哲学：**让会话重置摘要直接复用策展记录生成**（CR-07-4 已规定长期记忆
   只注入相关记录，把同一原则用到重置路径），避免两套摘要机制漂移。
4. 注入顺序按 §1.2：稳定锚点在前、delta 摘要在动态区。

### 2.2 重置触发：70% 固定阈值需要证据校准 + 任务边界压缩（P1）

**依据**：
- **Context Rot**（Chroma Research，2025-07，18 个前沿模型、194,480 次调用）：所有模型随
  输入变长而**连续**退化，远早于窗口填满；三个机制叠加——lost-in-the-middle（U 型注意力）、
  干扰项（语义相似但无关的内容危害最大，单个干扰项即可见退化、四个显著叠加）、信噪比
  稀释。含义：「窗口 70%」是容量视角，不是质量视角；review diff 这种「相似干扰项密集」
  的场景可能 50% 就该动作。
- **Acon 阈值消融**：压缩太勤掉点、太疏费钱，中等阈值最优（其设定 history 4096 /
  observation 1024 tokens）——阈值必须按自己的任务分布标定，不能照搬。
- **SelfCompact（arXiv:2606.23525）**：让 agent 在子任务刚收敛的边界自主压缩，比固定间隔
  摘要省 30–70% token（论文口径）。

**落地建议**：
1. `needsAutoReset` 增加第二维信号：除 token 占用比外，记录「相似内容密度」代理指标
   （如本次注入中 diff/工具输出占比），review 类任务用更低阈值；用 bakeoff 做阈值扫描
   （50/60/70/80%）找本项目任务的拐点，而不是拍 70%。
2. 利用现成的**任务边界**：每个 task 完成（MISSION_REPORT 落盘）时做一次轻量增量整理
   （§2.1 的 delta 入账），把大压缩摊到边界上，替代「撑到阈值一次性重建」。
3. 档位 B（per-mission）也接入同一套信号，而不是只有 C 档受益。

### 2.3 重置后保留 verbatim 近期窗口（P1）

**现状**：重置摘要「不含原始对话与叙事（S5）」——干净，但进行中任务的最近工具结果/ steer
可能在重置瞬间丢失，造成「重置后断片」。

**依据**：Claude Code auto-compact（默认约 150K input tokens 触发）采用混合策略：用户消息
**逐字保留**、assistant 回复与工具结果压缩，并支持 `pause_after_compaction` 在续跑前注入
最近若干条**原样**工具结果（Zylos 技术分析，二手口径）。**CaT（Context as a Tool，
arXiv:2512.22087）**把工作区显式分三层：稳定任务语义 / 压缩长期记忆 / 高保真短期交互。

**落地建议**：context builder 第 3 段（重置摘要）之后固定增加「近期窗口」：该员工**当前
在途任务**最近 N=2–3 条原始事件（steer、tool 结果、task_question 问答）逐字注入，任务
结束即清空。它不跨任务、不叙事，因此不违反 S5；成本很小但能堵住重置断片。A/B 指标：
重置后首轮的澄清请求率/错误率。

### 2.4 N2 缺口接线：宿主侧检索注入，worker 仍零记忆工具（P1）

**现状**：worker 的 allowedTools 只有基础五件套，记忆读写走 commander，运行时自动注入
worker prompt 未接线（N2）。

**依据**：
- **Mem0**（arXiv:2504.19413，2025-04）：动态提取-合并-检索，带 ADD/UPDATE/DELETE 冲突
  消解；LOCOMO 基准上 LLM-judge 比 OpenAI 原生记忆相对 +26%；相对全量上下文回放，工程
  汇总口径约省 90% token（Groundy 对比表，二手）。
- **A-MEM**（arXiv:2502.12110）：Zettelkasten 式，每条记忆带上下文描述/关键词/标签并自动
  双向链接、回溯更新旧条目，多跳更强、比 MemGPT 式虚拟上下文省 token。
- **本项目自测**：记忆 A/B（10 对）平均省 5,602 tokens/任务、7/10 胜——**自有数据已经正向**，
  缺的只是接线。

**落地建议（保持三道防线不变）**：
1. 检索发生在**宿主**：派发前由编排器用 task spec 对 `owner_slot_id` / `team:<mission_id>`
   范围内的策展记录做 top-k（关键词/BM25 起步，与 §1.1 tag 过滤同基建），结果作为 context
   builder 的一个固定段落注入；worker 进程依然看不到 pod_mem_* 工具，白名单防线不动。
2. 只注入相关记录（CR-07-4 不变），每条带来源与关系类型；无相关记录时整段省略（空输入
   保护）。
3. reflection 的合并逻辑可借 Mem0 的冲突消解：新事实与旧记录矛盾时走 contradicts 标记 +
   commander 收口，而不是并存（「住北京」「搬上海」问题）。
4. 先接 per-mission team 记忆（收益面最大），个体记忆第二阶段。

**验证**：扩大记忆 bakeoff 样本到统计显著（10 对偏小，措辞实验已证明小样本下 Δ=45 都不
显著），主指标 tokens/任务 + 成功率，按团队/个体分层。

### 2.5 安全锚点在压缩中的保真（P1，测试化）

**依据**：**TypeCompact / Compaction Cliff（arXiv:2608.22752）**指出压缩会静默抹掉安全
约束（governance decay），其分类型保真压缩在各压缩比下保留的安全规则是最强单遍 LLM 压缩
器的 2–4×；做法是安全规则**复制钉住（pin）**、不参与摘要。

**落地建议**：tenets、charter 纪律、路径白名单提示属于「永远逐字、永远最前」的 pinned
层，任何重置/delta 压缩/记忆注入都不得改写或概括它们；现状架构上 tenets 独立前置注入已
是对的，补一条**不变量测试**：任意一次 buildTaskPrompt 输出中，pinned 层文本与模板逐字
相等（与 §1.2 前缀 hash 测试合并实现）。

### 2.6 记忆架构横向参照（不建议照搬，记录取舍理由）

- **MemGPT/Letta**：OS 式分页（core memory 页换入换出），适合单长会话 agent；本项目是
  进程级 worker + 宿主记忆，分页由会话三档承担，不需要引入。
- **Hindsight（2025-12）/ AdMem（2026）**：区分 world fact / experience / belief 与
  semantic/episodic/procedural 分层；项目当前 typed relation 图谱够用，若后续记忆类型变复杂
  可参考其四层网络分类，现阶段过度设计，记为备选。

## 3. 通信协议优化

### 3.1 ADOL：agent 数据层的四把刀（P2，逐项可落到 A2A/MCP/事件面）

**依据**：IETF 个人草案 `draft-chang-agent-token-efficient-02`（华为，2026-01-12；注意是
Expired Internet-Draft、无标准效力，但问题分类与机制有实测支撑，可作设计参考）。它指出
MCP/A2A 的四类 token bloat 并给出 ADOL 层，全部向后兼容：

| ADOL 机制 | 解决的问题 | 本项目落点 |
|---|---|---|
| **Schema 去重（JSON $ref）** | 同 server 工具重复 schema 片段；实测 GitHub 官方 MCP 60 工具中重复率 9.84% | pod_* 工具的公共参数（mission_id/task_id/slot_id、分页/游标字段）抽共享定义，commander 工具清单与 `mcp-server.ts` 同步 |
| **可选字段自适应（tools/list --short）** | output schema/metadata 非必需却全量下发 | 与 §1.1 合并：默认 short（name+一句话+tag），展开时才给完整 JSON Schema |
| **requireOutput 字段投影** | server 永远按 schema 全量返回，调用方只要其中两三个字段 | ① MISSION_REPORT 允许派发方声明所需 section；② SSE/A2A 订阅支持字段级投影（前端列表只要状态字段时不回整对象）；③ fs-browse 返回按请求裁剪 |
| **检索式工具选择** | 工具列表越长选择越差 | §1.1 的 stage tag 过滤即其 Approach 2（标签版，零模型成本） |

草案安全提示也值得抄：embedding 检索不要明文外传、外部 $ref 只引可信源（防 schema
投毒）——本项目 loopback 面风险低，但 MCP 反向暴露面要守。

### 3.2 worker ↔ 编排器 wire：结构化错误码替代自然语言 stderr（P2）

**现状**：stdout 逐行 stream-json；stderr 取最后 ~12 行做失败根因（401 等）。问题：12 行
自然语言要 commander/编排器再解读，既花 token 又不稳定（措辞一变解析就漂）。

**建议**：在 result 事件之外约定一行**有界结构化错误信封**
（`{"error_code":"AUTH_401","retriable":false,"hint_ref":"..."}`，hint 文本进事件审计但
不进 LLM 上下文），编排器按 code 走确定性分流（正好喂给现有 P1 feedback 环的结构类/语义类
分流）；stderr 12 行降级为纯调试材料，只在转人工时给人看。注意区分：**给机器的用短码、
给人的留全文**（审计面不变），这也是 ADOL「verbose 可控」原则。

### 3.3 A2A 面对齐 v1.0（P2，按需）

**现状**：Agent Card + sendMessage[Stream] + JSON-RPC，Task=mission，SSE，loopback NoAuth。
A2A 已于 **2026-03-12 发布 v1.0**（Linux Foundation 托管，150+ 组织、6 语言 SDK）。对照后
本项目已符合的点与可补点：

- **已符合/方向正确**：SSE id 精确游标 + replay + 轮询兜底，对应 v1.0「任务生命周期独立于
  单条流、断流重连不影响 task、多流同序」；任务状态机与内部 task-machine 对齐。
- **可补 1：Push Notification（webhook 回调）**。长任务（mission 常跑百秒到千秒）不必让
  客户端挂 SSE 长连；cron 触发的任务完成后回调 IM 通道是天然场景（`channel-im.ts` 已在）。
- **可补 2：Signed Agent Card**。v1.0 强调 card 签名防发现环节被投毒；当前 loopback NoAuth
  没问题，一旦跨机/上网络这是第一道，提前在 Agent Card 里留签名扩展位。
- **状态词汇对齐**：v1.0 非终态 submitted/working/input-required/auth-required，终态
  completed/failed/canceled/rejected；内部状态机映射时补 `input-required`（对应现有
  task_question/need_clarify）与 `rejected`（能力拒绝，对应 P1 feedback 环语义类拒绝）的
  显式映射，外部驱动方才能正确处理「要人补信息」与「拒单」两种停顿。
- **成本意识**：A2A 委派是双边计费（消息双方都过模型），有测算称一次委派 ≈ card 800 +
  任务 250 + 对侧 1200 tokens（howaiworks 汇总，二手口径）。本项目「指令进/摘要出」、
  review 排除实现者叙事的原则应推广到**所有**跨员工/跨 agent 传递：给人看的 relay 留痕与
  给下游模型的最小 spec 永远是两个版本。

### 3.4 明确「不适用」清单（避免白费功夫）

- **隐式通信（latent communication，arXiv:2606.05711，传 embedding/hidden state 代替自然
  语言）**：要求双方同模型/可共享隐状态。本项目 worker 是异构厂商 CLI（claude/codex/
  opencode/ark），不成立，排除。
- **模型侧 KV cache offload / PagedAttention 等推理优化**：worker 走厂商 API，非自控推理
  层，只能用 §1.2 的前缀缓存对齐，不涉及自建。
- **JSON 行二进制编码（MessagePack 等）**：进程内 wire 字节不进 LLM、不花 token，现状
  JSONL 的可审计性价值更高，不为省几个网络字节改。

## 4. 落地路线图（建议）

| 阶段 | 动作 | 涉及模块 | 依据 | 验证口径（沿用 bakeoff 文化） |
|---|---|---|---|---|
| P0-1 | 工具分层加载（stage tag 过滤 + expand 元工具） | commander.ts、mcp-server.ts、工具定义处 | RAG-MCP / ToolRAG / DTL / ADOL | by_stage 每轮 input tokens；工具误选率；成功率不回归 |
| P0-2 | 静态前缀工程 + 前缀 hash 快照测试 + 缓存命中列 | buildTaskPrompt/buildPlannerSpec、ledger.ts、各 vendor adapter | Anthropic/OpenAI caching 文档 | cached_input 占比；重试二次计费 token |
| P1-1 | 重置摘要 ACE 化（条目化 delta 账本，复用策展记录） | session-tiers.ts、memory.ts、orchestrator.ts | ACE | 多次重置后任务成功率；摘要 token；重置后澄清率 |
| P1-2 | 重置阈值标定 + 任务边界增量整理 | session-tiers.ts、orchestrator.ts | Context Rot / Acon / SelfCompact | 50–80% 阈值扫描 bakeoff；各档任务成功率-成本曲线 |
| P1-3 | 重置后 verbatim 近期窗口（N=2–3，在途任务） | context builder | CaT / Claude Code 实践 | 重置后首轮错误率/澄清率 A/B |
| P1-4 | N2 接线：宿主侧 top-k 记忆注入 worker | orchestrator 派发路径、memory.ts | Mem0/A-MEM + 自测 5,602 tokens 正向 | 扩大样本的记忆 A/B，分层显著性 |
| P1-5 | review hunk 两级加载 + 截断元数据 | review spec 生成处、verifier.ts、fs-browse | Agentless / SWE-Edit / SWE-Pruner | review token、缺陷发现数、误报率 A/B |
| P1-6 | pinned 安全层逐字不变量测试 | 测试基建 | TypeCompact | CI 不变量测试 |
| P2-1 | ADOL：$ref 去重、--short、requireOutput 投影 | mcp-server.ts、a2a.ts、routes/SSE | IETF ADOL | 工具清单字节数；投影前后响应 token |
| P2-2 | worker 结构化错误信封 | vendor adapter、orchestrator 分流 | ADOL verbose 控制 | 失败分流准确率；根因不再进 LLM 上下文的比例 |
| P2-3 | A2A v1.0：push 通知、状态映射、card 签名位 | a2a.ts、cron.ts、channel-im.ts | A2A v1.0 规范 | 联调演示；长任务不挂长连的资源占用 |
| P2-4 | 自然语言压缩小实验（IM/摘要场景，Acon 路线） | channel-im、reflection | Acon / LLMLingua-2 | 小样本 A/B，无显著收益即停（同措辞实验纪律） |

排序原则：P0 两项是「每轮/每次重试都在交的固定税」，改动局部、无模型依赖、收益确定；
P1 围绕上下文生命周期，彼此配套（delta 账本是阈值/近期窗口/记忆注入的公共底座，建议先做
P1-1）；P2 是协议整洁度与未来跨机准备。
