### 安全守卫实测

| 用例 | 结果 |
|---|---|
| `Host: 127.0.0.1:3955` / `localhost:3955` | 200 放行 |
| `Host: evil.com` / `1.2.3.4:3955` / 空 Host | 403 DNS rebinding 拦截 |
| 跨站 `Origin`、`Origin: null`（沙箱 iframe 绕过） | 403 拦截 |
| 无 Origin（curl/原生客户端） | 放行至业务逻辑 |
| `text/plain`、`x-www-form-urlencoded` 带 body 的 POST | 400 拦截 |
| `application/json` | 放行至业务逻辑 |

> 注意：用 Node `fetch` 设置 `Host` 头测**不可行**——undici 会忽略该头，得到假阴性 200。

## 三、发现的问题

### ~~P1~~ → P2 — eventsTail 高吞吐丢事件（边界 bug）【已修复】

> 严重度下修：SSE 主路径走 `eventsAfter()`（无上限）是安全的，
> 丢事件只发生在 SSE 降级到 HTTP 轮询时。
>
> **修复**：`eventsTail(afterTs, afterId?)` 返回 `{ events, cursor, has_more }`——
> afterId 按排序后位置截断（同毫秒事件不会被 `ts > after` 整批跳过），
> 窗口取**最早**一批并置 `has_more` 供客户端续读；afterId 失效回退 ts 语义。
> 前端 `PodPanel` 改用事件 id 游标，`pollEvents` 遇 `has_more` 立即续读（上限 10 批）。

`src/pod-service.ts:595` 的顺序是 `filter(ts > afterTs)` → `sort` → **`.slice(-200)`**，
取的是**最后 200 条**。而 `orchestrator.handleProgress`（`src/core/orchestrator.ts:704`）
对每个流式 chunk **无节流**落一个事件。

当单个轮询周期内新增事件 > 200 时，较早的事件被丢弃，且前端 cursor 已推进到最新 ts，
被丢的事件**永不补偿** → 对话流丢内容。并行 agent 高速输出时容易触发。

修复方向：改为取最早 N 条（保证不跳号），或按 cursor 分页返回并带上 `has_more`。

### P3 — ledger 契约不一致（实测确认）【已修复】

> **修复**：`Ledger.summary()` 本来就返回完整 `LedgerEntry[]`，
> `ledgerTail()` 里多做的那次字段瘦身是契约缺口的来源——去掉即可。
> 现在 `entries` 含 `slot_id / task_id / ts / price_table_version`，与 `api.ts` 声明一致。
> 运行时无变化（前端此前只取 `tokens_in/out`、`equiv_usd`），属消除类型谎言。

`api.ts` 的 `LedgerEntry` 声明含 `slot_id / task_id / ts / price_known / price_table_version`，
但 `ledgerTail()` 实际返回瘦身对象（缺这 4 个字段），实测归档返回的 `model` 为空串。
运行时暂无影响（前端只用 `tokens_in/out`、`equiv_usd`），但类型声明比实现宽，属契约缺口。

### P4 — 边界与体验

1. `fs-browse` 300 条上限**无截断提示**，用户会以为目录列表不全。
2. `listDrives()` 从 `A:` 遍历到 `Z:`（含软驱位）。
3. `missionArchive` 返回全量事件**无上限**，长会话归档响应体会膨胀。
4. mission 结束后 `/status` 返回 `mission: null`（只返回 active），前端会跳空态。
5. `budget_usd: 0` 归一为 1e9 后直接暴露在 `/missions` JSON；前端按 `budget_tokens`
   判断「不限」、不显示 USD，故仅 API 面不优雅，非缺陷。
